# PDF由来商品の仮登録・確認フロー 改修方針書

作成日: 2026年11月11日（日本時間）

## 1. 目的と前提

PDF解析で既存商品に一致しない明細も、仮登録として商品検索・一覧から利用できるようにする。利用者は注意表示から元PDFと類似候補を確認し、その場で確定・修正・統合する。全明細の事前確認を必須にせず、商品マスタの精度と確認作業の効率を両立する。

`db/schema/v3_product_review.sql` は、ユーザーよりDBで実行しエラーなしとの報告を受けている。アプリ実装前に接続先環境と追加列・制約・テーブルの存在を読み取り専用で照合する。本書作成時点ではアプリ改修・データ移行を実施していない。

本番マイグレーションは人が手動実行する。Vercel・Neonの設定、権限、課金に関する操作は人が行う。アプリ内認証は追加せず、アプリとPDFへのアクセスを外側の保護で制御する。

## 2. 現状と確認済みの事実

2026年11月11日の調査時点で、接続先DBには次の解析結果があった。件数は商品数ではなく抽出明細数であり、移行前に再集計する。

| ファイル    | ページ数 | 抽出明細 | 新規商品候補 | 商品未照合 | 単価登録履歴 |
| ----------- | -------: | -------: | -----------: | ---------: | -----------: |
| 納品書1.pdf |       30 |       76 |           64 |          6 |            6 |
| 納品書2.pdf |        3 |        4 |            4 |          0 |            0 |
| 合計        |       33 |       80 |           68 |          6 |            6 |

- 新規商品候補68明細は解析済みでも商品マスタに存在せず、通常の商品検索に出ない。
- 単価登録6明細は既存商品に対する仕入先別単価の新規追加であり、既存単価の上書きではなかった。
- 現在の解析処理は正規化した商品キーで照合し、メーカーを含まない旧形式キーも照合に使用する。
- `system_confidence` はモデル出力への加減点であり、正答確率ではない。1.000を根拠に確認済みにはしない。
- 現在の `buildLineItemRow` は `productMaker` を保存していない。今後は保存し、過去明細の欠落を補う場合は差分の `after.productMaker` などの出典を確認する。商品キー文字列からの推測でメーカーを確定しない。

## 3. 改修範囲

1. Drizzle定義・取得型を実行済みスキーマに合わせる。
2. 未照合明細の仮登録、出典の保存、再取込時の重複防止を実装する。
3. 商品検索・一覧・詳細・表形式画面に確認状態とPDFリンクを追加する。
4. 類似候補の根拠表示、確定・修正・統合の操作を実装する。
5. 仮登録と統合済み商品に対する自動更新を制御する。
6. 検証後に今回の68明細を対象とするデータ移行を行う。

商品未照合6明細は新規商品候補68明細とは区別する。自動仮登録に必要な情報が不足する明細は要確認一覧に残し、無理に商品化しない。過去の全PDFを一括移行する作業は別途対象を定める。

## 4. 商品の状態と表示

| DB状態         | 表示                       | 意味・扱い                                 |
| -------------- | -------------------------- | ------------------------------------------ |
| `LEGACY`       | 既存データ                 | 導入前の商品。人が確認済みという意味はない |
| `PROVISIONAL`  | 赤字＋「⚠ 仮登録・未確認」 | PDFから作成された未確認商品                |
| `NEEDS_REVIEW` | 赤字＋「⚠ 要確認」と理由   | 情報の矛盾や確認が必要な商品               |
| `VERIFIED`     | 確認済み                   | 人が内容を確認し確定した商品               |
| `MERGED`       | 統合済み・統合先へのリンク | 通常の検索・一覧・自動照合から除外する     |

`quality_flag` は既存の品質情報として維持し、`review_status` と分けて扱う。色に加えて文字ラベルを表示する。

基本遷移は `PROVISIONAL / NEEDS_REVIEW / LEGACY → VERIFIED`、問題発見時は `VERIFIED → NEEDS_REVIEW`、商品統合時は統合元を `MERGED` とする。修正だけでは確認済みにせず、明示的な確定操作を必要とする。確認日時・確認者は最新の確認操作を表し、過去の経緯は履歴に残す。

## 5. PDF解析・仮登録の処理

### 5.1 登録条件

- 解析が成功し、商品名と安定した商品キーを生成できる明細を対象とする。
- まず現在の出典紐付けを確認し、次に統合済みを除いた商品キーの完全一致を調べる。
- 完全一致商品がなければ仮登録する。類似候補があっても自動統合しない。
- 信頼度不足、単価・仕入先不足、計算不整合などは注意理由として保持する。商品を作成できる条件を満たさないものは既存の要確認明細に残す。
- PDF由来の新規作成では `review_status` を明示する。DB既定値の `LEGACY` に任せない。

### 5.2 保存と再実行

商品、必要な仕入先単価、`product_document_sources`、作成履歴を同一トランザクションで保存する。商品キーの一意制約と明細IDの主キーを利用し、競合時は既存行を再取得する。解析APIの再送、並行処理、同一PDFの再解析でも商品・単価・履歴を重複作成しない。

同一商品の別明細は同じ仮登録商品へ出典を追加する。単位・口径・型番などが異なる商品を曖昧一致でまとめない。手動修正した値を再解析結果で戻さない。

過去に人が統合した明細は、出典の現在の紐付け先を優先する。新しい明細が統合元キーに一致した場合は、統合先を確認候補として提示し、統合済み行の再使用や同じキーの新規作成を避ける。

### 5.3 単価の扱い

- 仮登録商品の有効な仕入先・単価は保存して検索できるようにする。商品と価格が未確認であることを併記する。
- 単価が取得できない場合は0円で補わず未設定とし、価格行なしでも商品が検索・一覧に出るようにする。
- 仮登録・要確認商品の再取込では、別の抽出値を出典明細として保存し、既存単価を無条件に上書きしない。未設定からの単価追加も未確認のまま履歴を残す。
- 確認済み商品・既存商品の通常更新には、現在の信頼度・価格差・日付の条件を維持する。旧形式キーだけでメーカーの矛盾を無視しない。
- 同じ仕入先で価格が競合する場合、出典日付と値を並べて選択させる。仕入先別単価の欠落を価格差0として扱う既存仕様は、確認画面で「比較元なし」と表示する。
- 商品の確認済み状態は、将来取り込むすべての価格を承認した意味にはしない。未反映の価格候補は解析差分に保持し、確認導線を残す。

## 6. 出典PDFと類似候補

出典は `product_document_sources.line_item_id → document_line_items.parse_run_id → document_parse_runs.document_id → documents` で取得する。URLをマスタに固定保存しない。

一覧には代表出典と出典件数を表示し、詳細では全出典を閲覧できるようにする。表示例は「納品書1.pdf・1ページ目／売上日2026-11-04」。分割された該当ページを直接開き、可能なら画面横にプレビューする。初期実装では該当ページを開く機能を必須とし、明細位置の自動ハイライトは別対応とする。

PDFは保護されたアプリ経由で配信し、任意URLの取得を受け付けない。ストレージの秘密情報や永続的な公開URLをクライアントへ渡さない。削除済み・取得不能のPDFは理由を表示し、元の出典履歴は残す。

類似検索はメーカー、商品名、型番、規格から候補を絞り、上位数件を表示する。候補には一致項目と相違項目を必ず付ける。口径・寸法・単位の違いを重視し、同名だけで同一商品と判定しない。候補なしは「類似候補なし」と明示する。

`match_candidates` には照合時点の候補をスナップショット保存する。これは候補であり確定リンクではない。確認時には候補の現在の状態を再取得し、削除・修正・統合による変化を検知する。順位や一致項目を表示し、根拠のない正答率は表示しない。

## 7. 確認操作と競合制御

| 操作               | 保存する内容                                             |
| ------------------ | -------------------------------------------------------- |
| 別商品として確定   | `VERIFIED`、確認者・日時、`VERIFY`履歴                   |
| 読み取り内容を修正 | 商品・必要な単価の変更、`CORRECT`履歴。PDF抽出原文は維持 |
| 再確認を依頼       | `NEEDS_REVIEW`、理由、`REQUEST_REVIEW`履歴               |
| 既存商品へ統合     | 出典の付け替え、元を`MERGED`、統合先ID、`MERGE`履歴      |

確認・修正・統合は商品と対象価格をロックするか更新前の値を比較し、競合時は再読み込みを促す。二重クリックで履歴や価格を重複登録しない。商品・価格・出典・各履歴は同一トランザクションで更新する。

統合先は非`MERGED`かつ確認済みまたは既存の商品に限定し、自分自身への統合と循環を禁止する。統合元は削除せず、直接アクセス時は統合先を案内する。仕入先単価が競合した場合は自動で上書きせず、利用者が選択する。統合先の全体状態を自動で`VERIFIED`に変更しない。

`product_review_history` に商品・関連価格・出典紐付けの変更前後と理由を保存し、単価変更は従来の `update_history` にも保存する。確認者名は必須入力とするが、アプリ内認証がないため本人認証の証跡としては扱わない。システム処理は `system:pdf-parse` 等で区別する。

履歴は調査・復旧に利用する。ワンクリック取消は初期範囲に含めず、復旧時は後続更新を確認して履歴に基づく補正を行う。

## 9. 今回の68明細の移行

対象取込グループ:

- 納品書1.pdf: `b8eb3971-2e56-4f44-a643-2312ed2ae79b`
- 納品書2.pdf: `3206a804-55dc-49a7-bc58-6cfa8e406e1f`

1. 最新の成功解析と既存の手動紐付けを再取得し、移行対象を固定する。古い再解析結果や削除済みPDFを混ぜない。
2. ドライランで対象明細数、重複集約後の商品数、価格競合、スキップ理由を出力する。
3. アプリの仮登録サービスと同じルールを使用し、既存商品がある場合は新規作成せず照合する。
4. 手動実行で移行し、出典・作成履歴・必要な価格履歴を残す。既存6明細の価格履歴は変更しない。
5. 再実行して追加作成がないこと、対象が検索できること、PDFを開けることを確認する。

68明細から68商品が作られるとは限らない。未照合6明細は別集計し、情報不足のものを自動登録しない。

## 10. 検証と受入条件

- WTP150の対象商品を検索すると、仮登録ラベルと「納品書1.pdf・1ページ目」のリンクが表示される。
- 同じ商品を再取込しても商品は増えず、別の出典は保持される。別口径の商品は混ざらない。
- 価格なしの商品も検索でき、未設定を0円として表示しない。
- 仮登録への再取込で確認済みへ昇格せず、競合単価・手動修正値を自動上書きしない。
- 候補の一致・相違が表示され、候補更新後の古い情報で統合できない。
- 確定・修正・統合の履歴が残り、競合・二重送信・途中失敗でも部分更新が残らない。
- 統合済み商品が通常検索・自動照合に出ず、元レコードから統合先と出典を追える。
- 保護されたPDFの表示、削除済みPDF、取得失敗、外部からの直接アクセスを確認する。
- 既存の単価更新ルール、Excel取込、手動編集の回帰を確認する。

重点条件を単体テストとDB結合テストで検証し、代表的な操作をブラウザで通して確認する。変更範囲に応じて `pnpm lint`、`pnpm typecheck`、`pnpm test`、`pnpm build` を実行する。本番DBをテストの書き込み先にしない。

## 11. 実装・リリース順序

1. スキーマ整合、状態別の読み取り・注意表示・PDF閲覧を実装する。
2. 仮登録・出典・履歴保存と自動更新制御を実装する。
3. 確定・修正・統合と類似候補表示を実装する。
4. Previewの検証環境で一連の操作と競合処理を確認する。
5. 状態表示と更新制御が揃った版を本番へ反映する。
6. ドライラン結果を確認して68明細を手動移行する。

1 PR = 1 concernを守り、各段階の差分を分ける。表示と更新制御が揃う前に本番で仮登録の作成を開始しない。追加DDLが必要になった場合も自動実行せず、別の手動SQLとして提示する。

本番反映後に問題が出た場合は、新規仮登録・自動書き込みを停止し、出典と履歴を維持する。仮登録を認識しない旧版への単純な巻き戻しは、自動照合の誤動作につながるため行わない。状態制御を残した修正版で復旧する。

運用効果は、仮登録数、確認・統合に要した操作数、重複商品数、誤反映件数で評価する。確認が進んだ割合だけを精度の指標にしない。
